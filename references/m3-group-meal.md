# M3 多人拼餐计算器

**本 Skill 的核心竞争力。** 输入人数和预算，输出几套可直接下单的方案，算出含优惠的实付总价与人均，
并挑出最省的一套。走**企业团餐（beType=6）**，因为只有团餐场景能拿到满减满折规则与助餐服务。

---

## 0. 为什么用团餐而不是麦乐送

| 能力 | 麦乐送(beType=2) | 团餐(beType=6) |
|---|---|---|
| query-promotions（满减/满折原始数据） | 不可用 | **可用** |
| query-meal-assistance（助餐服务） | 不可用 | **可用** |
| query-meals 内置人均档位搭配规则 | 无 | **有** |

三者凑齐，「输入预算+人数 → 输出最优方案」才成立。用麦乐送做拼餐只会退化成「多点几份」，没有差异化。

---

## 1. 输入

| 输入项 | 是否必需 | 说明 |
|---|---|---|
| 人数 | 是 | 如 5 人 |
| 总预算 或 人均预算 | 是 | 只给一个时，另一个反推 |

**人均预算 = 总预算 ÷ 人数**（只给人均时，总预算 = 人均 × 人数）

---

## 2. 工具链

```
前提：已具备 M2 的外送上下文，且 beType=6、orderType=2、addressId、storeCode、beCode 齐全。
      若当前是 beType=2，先重取 beCode（见 m2 文档 3.4）。

① query-promotions(
     storeCode = <ctx.storeCode>,
     beCode    = <ctx.beCode>,
     orderType = 2,
     beType    = 6
   )
   → 拿满减满折规则，推算「凑单门槛线」
   → promotionType: 31=满额减，33=订单折扣
   → ruleCategory: 30=满折/折扣，40=满减

② query-meals(
     storeCode = <ctx.storeCode>,
     beCode    = <ctx.beCode>,
     orderType = 2,
     beType    = 6
   )
   → 拿全量餐品 + productCode + 价格
   → 结合人均档位生成 3 套候选方案

③ query-meal-assistance(
     storeCode = <ctx.storeCode>,
     beCode    = <ctx.beCode>,
     orderType = 2,
     beType    = 6
   )
   → 展示助餐服务选项让用户选 → 取 gmServiceCode
   → 实测：GMS002 / GMS003 仅 07:00-20:00 送达时段可用，凌晨/清晨下单通常只有
     GMS001（保鲜速达）；直接把 enable=true 的选项给用户选即可

④ calculate-price(...) × N 套方案（并行）
   {
     storeCode     : <ctx.storeCode>,
     beCode        : <ctx.beCode>,
     orderType     : 2,
     beType        : 6,
     gmServiceCode : <③选定的助餐服务 code>,
     items         : [{ productCode, quantity }, ...]
   }
   → 返回价格单位为「分」，÷100 转元后再展示

⑤ 比价选优 → 展示方案对比

⑥ create-order(...)
   {
     storeCode, beCode, orderType:2, beType:6,
     addressId     : <ctx.addressId>,
     gmServiceCode : <ctx.gmServiceCode>,
     items         : <用户选中方案的 items>
   }
   → 不要传 takeWayCode（外送禁止）
```

**可选环节**：用户要改套餐组成或特调时，先调
`query-meal-detail(storeCode, beCode, orderType=2, beType=6, code)` 拿到 modification 选项。
特调 key 规则见 SKILL.md 易错点第 5 条。

## 3. 人均档位搭配规则（来自 query-meals 官方规则，必须遵循）

| 人均预算 | 搭配模板 |
|---|---|
| < 20 元 | 小食 |
| 20-30 元 | 汉堡 + 小食 或 汉堡 + 饮料 |
| 30-40 元 | 汉堡 + 薯条/小食 + 饮料 |
| 40-50 元 | 汉堡 + 薯条 + 小食 + 饮料 |
| > 50 元 | 丰富组合，优先不重复小食 |

档位用于生成**基础方案（方案 B）**，另外两套在此基础上做变体。

---

## 4. 三套候选方案生成策略

| 方案 | 生成策略 | 适用场景 |
|---|---|---|
| **A 省钱型** | 贴近凑单门槛下限，优先让满减后实付最低 | 预算紧张 |
| **B 均衡型** | 严格按人均档位模板，品类最均衡 | 默认，大多数情况 |
| **C 凑单型** | 在 B 基础上加 1-2 件，凑到满减门槛 | 差几块钱到门槛时 |

### 4.1 凑单反差（本模块最打动人的一点）

主动计算这件事：**多买一件，总价反而更低**。

**前置判断（实测教训）：先看差额。** 团餐折扣门槛实测为 **300 / 500 / 1000 / 2000 元，
且是折扣制（7.8/7.4/7.0/6.6 折），不是满减**。若从当前预算到最近门槛的差额过大
（如预算 150 → 门槛 300，差 150 元），**直接放弃 C 方案**——凑单代价远超折扣收益，
硬凑会误导用户（实测 150 元预算下 C 方案实付 ¥246，反而比 B 贵 ¥90）。
只有加 1-2 件小食就够到门槛时才生成 C。

计算方式：
```
若 实付(B) - 实付(C) > 0 且 C 比 B 多出商品
→ 说明 C 用更少的钱买到了更多东西，强推 C，并标出差值
```

示例话术：「选 C：多 2 件小食，总价反而少 10 块。」

只有在真的更便宜时才推 C，凑不满就别硬凑。

### 4.2 凑单门槛的应用

从 `query-promotions` 拿到规则后，先算出门槛线：

```
满 120 减 20 → 门槛线 120
满 150 减 30 → 门槛线 150
```

- 方案 A：目标实付最低，不刻意凑单。
- 方案 C：在 B 之上加最便宜的 1-2 件小食，把原价抬过门槛线。

---

## 5. 比价与推荐

三套方案各自 `calculate-price` 后，按以下优先级推荐：

1. **实付总额最低** → 标记「最省」
2. **若 C 触发凑单反差** → 标记「推荐 C」，并说明反差值
3. 并列时用**品类丰富度**兜底

推荐必须给理由，不能只说「推荐 A」。

---

## 6. AA 分账输出

```
人均 = 实付总额 ÷ 人数
```

- 能整除 → 直接给每人金额。
- 不能整除 → 按人数分摊到角，尾差让其中一人多担 1 元，并写清楚：
  「4 人付 24 元，1 人付 25 元」。

---

## 7. 输出

按 `references/output-templates.md` 的「拼餐方案对比卡片」渲染。要点：

- 顶部一行讲清：几人、总预算、人均。
- 三套方案并列，每套给出原价、满减后、人均、内容清单。
- 明确标记「最省」和「推荐」。
- 有凑单反差时单独用一行说明。
- 结尾给 AA 金额和「回复『下单 X』继续」。

**只给三套。** 不要罗列更多，选择越多越难决策。

---

## 8. 降级策略

| 情况 | 处理 |
|---|---|
| **预算够不到折扣门槛（实测 300 元起，折扣制非满减）** | 明确告知「团餐折扣 300 元起，当前预算触发不了」，只给 A/B；像实测那样说实话：「A/B 省的只是打包费减免，不是餐品折扣」，不要默认「凑满减」 |
| 人数未达团餐门槛 | 降级 beType=2 麦乐送，明确告知「人数不够团餐门槛，已切麦乐送」 |
| 预算过低（人均 < 20） | 仍走团餐，但只出小食类方案 |
| 该门店不支持团餐 | 降级 beType=2 并重取 beCode，告知用户 |
| 无可用满减规则 | 跳过 C 方案，只给 A/B，不要假装有满减 |

---

## 9. 常见错误

- **忘记传 gmServiceCode** → 团餐计价必失败。④ 之前必须有 ③ 且用户已选定。
- **用了 beType=2 的 beCode** → 切团餐时 beCode 会变，必须重取。
- **价格没 ÷100** → 会把 13800 显示成 13800 元。
- **凭空编造 productCode** → 一切商品 code 必须来自 `query-meals` 的返回。
- **没算满减就说最省** → 必须以 `calculate-price` 的实付结果为准，不要用原价排序。
